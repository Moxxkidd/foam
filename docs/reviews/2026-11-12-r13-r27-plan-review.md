# R13–R27 方案评估（2026-11-12）

评估基线：`842427f`（main；R01–R12 已完成，v0.1.3 已发布，v0.2.0 进行中）。
范围：路线图、版本清单与 R13–R27 开发文档；对照 R01–R12 已落地代码复核方案假设。
性质：方案评估与文档修订，不含产品实施或测试。本文保留评估时点结论；各条目后续状态以版本清单和 R 文档为准。

## 1. 总体结论

R13–R27 的规格写于 2026-09-26，早于 R06–R12 落地。方向（先正确性与证据、再体验、再兼容）仍然成立，无需推翻。主要问题有三类：

1. **两项影响完整性或可用性的缺口没有排进 v0.2.0**：TUI 不持单写者锁，审计链存在分叉路径；README 推荐的安装方式无法使用 protected 模式。
2. **部分条目与已交付内容重叠**：R18、R21 的多数验收项已由 R03/R09/R12 交付；R15 与 R13 各自定义状态读取。
3. **跨条目契约未统一**：运行状态有四套词汇；v0.3.0 依赖链全串行；若干规格与当前代码事实不符。

处置：新增 R28、R29（纳入 v0.2.0）和 R30（暂缓）；修订 R13–R27 中受影响的文档，并在各文档 §7 追加本次评估记录。

## 2. 发现与处置

### P0：影响正确性、安全边界或发布诚实性

**F1 TUI 不持单写者锁，审计链可分叉。**
R02 只给 run/resume 接了锁，TUI 未接（R02 §8 剩余风险）；R03 D3 维持不接。当前代码中 TUI 以 `RunRuntime(lock=None)` 运行。因此 TUI 运行期间，对同一目录执行 CLI `resume` 不会被拒绝，两个写者会同时追加 `audit.jsonl`，哈希链分叉。这件事只在 v0.3.0 的 R15 AC04 中被间接提及。
处置：新增 [R28](../items/R28.md)，纳入 v0.2.0，并排在 R13 之前；R15 AC04 改为依赖 R28。

**F2 protected 模式与推荐安装方式不兼容。**
protected 启动 helper 前，`_trusted_source` 要求解释器和 `network_helper.py` 的路径逐级为 root 所有，且不可被组或他人写入。README 推荐 `pipx install .`，pipx 把包装在用户目录，helper 源路径必然被判为不可信。R11 只在 Docker/linuxkit 中验证（路径全为 root 所有），没有覆盖真实安装形态。Kali 采用 PEP 668，`sudo pip install` 默认被拒；sudo 会清掉环境变量，密钥无法传入；root 写出的 0700 engagement，普通用户之后也无法 report/verify。这些部署细节都没有方案。
处置：新增 [R29](../items/R29.md)，纳入 v0.2.0；在 v0.2.0 发布门槛中增加「protected 受支持安装形态在真实 Kali 上验证，或在发布说明中如实标未验证」。不得为此放宽 `_trusted_source`。

### P1：方案过时或范围重叠，会导致返工

**F3 R18、R21 的验收项大量已交付。**
- R18：R09 已在每个有 `run_finished` 的终态生成确定性 manifest 和结项页，不调用 LLM；R12 已覆盖预算停止的 unfinished 证据；R03 的 `close_run` 已幂等，清理失败会如实上报。R18 实际剩下的是：带等待上界的「正常结束」动作，以及 TUI 内的结项展示与导航。
- R21：R12 已交付截断/缺终端标记流判为不完整（`test_token_limit_stop_reason_is_incomplete_error`、`test_missing_terminal_marker_is_truncated_stream`）、重试计入预算（`test_budget_includes_compile_retry_resume`、`test_total_budget_blocks_retry`）；`AuthError` 本就不可重试（`test_401_maps_to_auth_error`）；工具调用要等整轮流结束后才派发，失败的尝试会整体丢弃。R21 实际剩下的是：部分流工具调用的显式回归、live 支持矩阵和显式 failover。
处置：两份文档重划范围，已交付的 AC 改为「复核既有证据并引用」，不重复实现。

**F4 运行状态有四套词汇。**
loop `on_status`（running/paused/idle/stopped/killed/finished/error）、R13（run_state × liveness）、R16（run_state/tool_activity/waiting_reason/goal_status）、R18（execution/goal/cleanup/evidence_status）各自命名，路线图 §10 只写了语义要求。
处置：在路线图追加运行状态契约：持久事实以既有字段为唯一来源（loop status、R12 `goal_status`/`stop_reason`、R03 `cleanup_status`、R09 证据状态）；R13 和 R16 只做投影，不新增持久状态机；R18 只消费，不另存终态。R13、R16、R18 文档相应注明。

**F5 protected 能力边界没有告知模型。**
protected 仅支持出站 L3/L4 白名单；raw socket、AF_PACKET（如 `nmap -sS/-O`）、入站回连监听（反弹 shell、msf handler）、主机名/URL scope 都不支持（R10 §6），但 system prompt 和工具地图都没写。模型会反复尝试，最后以权限失败告终，这正是 R14 要治理的重复动作和无解释等待。
处置：R14 新增 R14-D 分片与 AC06：告知执行模式能力边界，并把这类失败解释清楚。真正扩展能力的研究列为 [R30](../items/R30.md)（暂缓，有进入条件）。

**F6 R15 与 R13 状态读取重复。**
R15 自定义任务摘要字段，自行判定「陈旧 PID 不显示假在线」，与 R13 的 status 读取和活性判定重复。
处置：R15 的任务列表复用 R13 的只读 status 结果，不另写读取器。

**F7 R22 的环境与执行模式前提没有写明。**
交接记录中裸 Kali 的验证通道仍未恢复；MS2 等场景依赖反弹 shell 或 raw 扫描，在 protected 下不可行。
处置：R22 增加环境前提（可用的真实 Kali；不可用时条目阻塞，不以 macOS/容器替代），每个场景须声明执行模式。

### P2：排期与规格质量

- **F8 v0.3.0 依赖全串行。** R16 的事件投影（A/B）不依赖 R15，只有 C 片的界面落位需要；R20 的性能基线必须在 R15 改动 TUI 前采集，否则 AC06「与基线相比」没有可比对象。处置：放宽 R16 的依赖；R20-A 的基线采集提前到 v0.3.0 开工前。
- **F9 R19 键位建议风险。** 原建议「Enter 换行、Ctrl+Enter 提交」，但多数终端无法区分 Ctrl+Enter 和 Enter，用户可能根本无法提交。处置：改为默认建议 Enter 提交、Ctrl+J 换行（终端里 LF 与 CR 可区分），bracketed paste 粘贴不触发提交；仍须真实终端矩阵验证后冻结。当前输入框为单行 `Input`，作为基线记录。
- **F10 R14 依据不具体。** AC01 的「历史误报样本」没有指向具体语料；AC04 的「全局 idle timeout」与代码不符：当前没有空闲超时，只有每个 job 默认 1800 s 墙钟超时（可设为 null）和 LLM 首事件超时。处置：语料指向 known-issues ②⑦ 及其审计 seq；超时基线按代码事实改写。
- **F11 暂缓条目的进入条件状态没有更新。** R25 的 R07/R11 条件已满足；R26 的 R08/R09 已完成；R27 的「统一执行服务」已由 R11 的 ToolExecutor 部分满足。处置：在 deferred 清单补「当前满足情况」，各条目仍保持暂缓。
- **F12 模板残留。** R14–R27 的全局约束引用了仓库外的「executing-plans」流程，各文档也都没有实施前复核节。处置：统一改为按 AGENTS.md §7 执行；各文档 §7 声明开工前须按 R13 §2.1 的方式补代码复核。
- **F13 R23 与 R13 的衔接。** R23 对 R22 的依赖只在于真实环境验证；可信度改进应扩展 R13 doctor 的 `tools.inventory` 检查，不另起入口。处置：在 R23 中写明。

### 评估后无需结构性修改

R17（分页、证据约束、只读）、R24（可选、静态导出先行）、R26（隔离与删除设计先行）的方案与已交付契约一致，只追加评估记录。
