## 设计取舍

1. **ToolRegistry 可追加、容错优先**:`register_module(TOOL_SCHEMAS,
   dispatch)` 整组注册(WP-01 形状;WP-05 `session.py` 与 WP-06
   `state.py` 已确认同构,直接可挂),`register(schema, handler)` 注册
   单工具。模型发来未知工具名、非法参数(TypeError/ValueError)一律回
   error dict 作 tool 结果让模型自我纠正——不抛异常炸环(真实模型一定
   会犯这类错)。同名重复注册拒绝覆盖(编程错误,fail fast)。
2. **MalformedToolCallError 恢复协议**(K3 实测消化项):后端的不变量
   「ToolCall.arguments 必为合法 dict」不允许把坏 JSON 原文放进 assistant
   历史,故以**空参数重建该调用帧**(id 缺失时合成 `malformed-N`),坏
   JSON 原文(≤4000 字符)连同纠正说明走 tool 结果回灌;同轮已收齐的
   合法调用照常执行。连续 3 次仍坏判定模型无法自愈,run 以 error 终止
   (`test_malformed_consecutive_cap_aborts` 熔断)。
3. **幻觉执行纠正**(K3 A4 实测消化项):assistant 无 tool_call 且文本
   命中动作声明特征(已执行/已扫描/已记录… + 英文过去式)时,不当真,
   回「主环自动纠正」user 消息要求真正发 tool_call 或明确 finish。正则
   **宁宽勿严**:误报代价是多一轮纠正(连续 2 次预算耗尽后接受 finish,
   防纠正死循环),漏报代价是 engagement 记录被幻觉污染——后者更糟。
4. **首事件超时默认 30s**(K3 实测 max 16.24s,弃用常见 10s 默认;有
   常量级测试锁 ≥30s)。可重试错误(网络/超时/限流/5xx/流断)指数退避
   1/2/4…≤8s,RateLimit 尊重 `retry_after`,默认最多 3 次,每次记
   `llm_retry` 审计;provider 拒绝(审核/鉴权/坏请求)**不重试**,run
   直接 error——不改写 prompt 规避审核是红线。
5. **压缩两阶段**:字符数/4 粗估(规格认可)。先压旧 tool 结果——占位
   含落盘路径 + sha256(执行时登记的 hints 表),模型可用 read_output
   溯源;仍超限再压旧对话——assistant 压 content 但**保留 tool_calls**
   (OpenAI 要求 tool_calls 与 tool 结果严格配对,删消息会断协议)。
   受保护:全部 system 角色消息(system prompt 与 ENGAGEMENT.md 天然
   覆盖)+ 首条 user(objective)+ 最近 6 条窗口。每次压缩记
   `context_compressed` 审计(前后估算、两阶段各压几条、是否仍超限)。
6. **ENGAGEMENT.md 每轮必载**:固定为 messages[1](system 角色,天然
   落入压缩保护),每轮 LLM 调用前重读文件刷新——模型用 run_command
   写文件即更新(文件读写占位)。模板含 发现/凭证/进行中的工作/备注
   四节。WP-06 已先于本 WP 关闭,其 `state/files.py` 布局(根下
   ENGAGEMENT.md、outputs/、audit.jsonl)与本 WP cli 的临时布局**逐位
   一致**,接管是纯换实现:loop 的 `_read_engagement` /
   `_ensure_engagement_file` 换 WP-06 读写接口,cli 建目录换
   `Engagement.create`(见「留给后续 WP」)。
7. **kill = cancel 当前 turn + 清理路径杀全部活动 job**:`kill()` 只
   置旗标 + cancel run 任务;杀 job、写 `kill_switch` 审计都在 run 的
   清理路径完成(单线程语义下无竞态)。pause 用同一 wake 事件唤醒后
   复查旗标,clear 后再复查一次堵 resume 竞态。已知边角:kill 恰好
   打在**前台** run_command 上时,WP-01 的 supervise 协程被 cancel,
   清理路径对该 job 的 kill_job 会因 done 事件无人置位而等满 5s 守卫
   返回 error dict——但进程组确已被 SIGKILL(止损目标达成),error 如实
   进审计。后台 job 无此问题(测试覆盖)。
8. **审计新 kind 5 个**(WP-02 明示允许扩展):`run_started`(objective
   为操作员内容,记明文)/`run_finished`(final 文本是 LLM 内容,只记
   哈希与字符数)/`loop_correction`/`llm_retry`/`context_compressed`。
   `llm_exchange_meta` 的 prompt 哈希取自**当轮实际发送的消息列表**
   (压缩后),这正是 WP-10 replay 的比对基准。
9. **cli 初版只做 headless run**:argparse 子命令;`--backend` 二选一,
   密钥一律由各后端自己从 env 读(cli 不碰 key 本体,缺 key → ConfigError
   → 退出码 2)。`backend_factory` 参数是测试注入点(e2e 不走网络)。
   Ctrl-C 第一次走 kill switch(优雅,退出码 130),第二次 `os._exit(130)`
   强退(审计每条已 flush,不丢)。退出码:0 finished / 130 killed /
   1 error / 2 参数配置错误。插话在 headless v0 不接线(stdin 交互是
   WP-09/10 的事),loop 的 interject API 已就绪并有测试。
10. **exit_code 信号说明**:`describe_exit_code` 用 POSIX 标准编号硬编码
    表(不查 signal 模块,输出跨平台一致),-9 说明覆盖 kill_job/超时
    强杀/OOM 三种常见成因,注入 run_command 结果的 `exit_note` 字段。
11. **system prompt 结构**:角色(含「只有 tool_call 才算动作」前置纪律)/
    授权声明(scope 规则原文 + 文件来源 + 加载时间)/方法论骨架(明示
    非 playbook)/工具使用纪律(分页、后台、信号、工作笔记、产物只写
    engagement 目录;发现入库与会话两个占位如实标注「后续版本提供」)/
    工具地图注入点(WP-08)/红线五条。全文无品牌名(连平台名也不提,
    快照逐字锁定)。

## 踩坑

1. **引号把护栏目标藏进单 token**:测试初版用 `echo "recon 127.0.0.1"`,
   shlex 分词后 `recon 127.0.0.1` 是一个词元,护栏正确地未提取到目标
   ——断言 `targets==["127.0.0.1"]` 失败才反应过来。护栏行为本身正确,
   是测试命令写法问题(改 `echo recon 127.0.0.1`)。教训:写护栏相关
   用例时先想清楚 shlex 词元边界。
2. **压缩测试的算术要按字符/4 算准**:初版预算随手填,两个压缩用例
   失败——keep_recent 默认 6 条把 8 条的小对话几乎全保护(无可压对象),
   另一个预算值没算准导致阶段一不停在预期位置。修正:显式传小窗口 +
   按总字符数/4 精确定预算。教训:测压缩先算 `estimate_tokens` 再定
   阈值,别拍脑袋。
3. **ruff E501 对字符串内长行同样生效**:prompt 快照测试里「工具地图
   占位」渲染结果是单行 193 字符,烘进测试文件就超 E501;noqa 在字符串
   里无效(会变成内容)。解法:快照拆三段拼接,长行单独用括号拼接串
   表达(文本仍是硬编码副本,快照灵敏度不变)。
4. **并行关闭窗口的共享文件竞态**:本 WP 开发期间 WP-06/WP-05 先后关闭
   推 main,全仓测试数从 170 → 245 → 277;开工时读过的 HANDOVER/台账
   在关闭时已过时——关闭前**重读最新版再 append**(契约 §3 纪律),本次
   零冲突。`git status` 确认工作区只剩本 WP 文件未跟踪,他 WP 文件已入
   对方 commit。
5. **无 live 凭据**:本会话 `THEFORM_LLM_API_KEY` /
   `THEFORM_ANTHROPIC_API_KEY` 均未设置,真实模型 e2e 未跑。主环全部
   行为由 fake 后端按 WP-03 的 K3 实测事件形状(先文本后工具、流末
   usage、MalformedToolCall 抛法)合成覆盖;真实模型 smoke 待有凭据时
   用 `theform run` 直接补跑。

## 已知限制

- 幻觉执行检测是启发式正则:英文正常总结里的过去式动词可能误伤(代价
  一轮纠正,有预算上限);中文新说法可能漏(代价回到 K3 原生行为)。
- 压缩粒度为整条消息,无摘要式压缩(占位即全部);仍超限时如实记
  `still_over_budget` 继续跑(provider 超限会报 InvalidRequest 错误,
  run 以 error 终止)。
- ENGAGEMENT.md 不裁剪:模型若无限写大,受保护消息会持续膨胀(与
  WP-06 接管时一并考虑上限策略)。
- headless 模式无操作员输入面;`--max-rounds` 是唯一预算兜底阀(默认
  不限)。

### 结果

**exit 0,`finished`,6 轮,tokens 输入 20685 / 输出 1208。** K3 依次完成
四步链:合并命令取版本 → 探测本机(护栏日志 `放行:127.0.0.1`,目标提取
正确)→ python heredoc 把结构化结论写进 ENGAGEMENT.md「发现」节(含证据

```text

llm_exchange_meta → loop_correction →                        # 见下「纠正实录」
llm_exchange_meta → exec_request → exec_result_meta →
llm_exchange_meta → run_finished
```

### 幻觉纠正机制被真实触发(且是一次设计内误报)

K3 的首次收尾文本含「结论**已写入** ENGAGEMENT.md」——该写入动作在**前轮**
真实发生过,但本轮消息无 tool_call 且命中动作声明特征,主环按设计回灌纠正
(`loop_correction` 审计在案)。K3 的响应堪称教科书:「收到纠正。为避免仅凭
记忆下结论,我先做一次真实的核验调用」——随即 `sed` 读取 ENGAGEMENT.md 发现
节 + `ls` 核对 outputs/ 证据日志,确认盘上状态后才给出最终结论。这正是取舍 3
的设计预期:启发式**宁宽勿严**,误报代价是一轮纠正,而这轮纠正被模型用于真实
核验,反而提升了结论的证据质量。
