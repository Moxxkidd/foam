## 设计取舍

1. **schema 形状:provider 中立纯 dict**。`TOOL_SCHEMAS` 每项
   `{name, description, parameters(JSON Schema)}`——OpenAI 兼容格式与
   Claude 格式的最小公共超集,WP-03 适配层翻译,WP-04 直接注册,WP-06
   state 工具同构。`dispatch(name, arguments)` 是 WP-04 唯一入口;未知
   工具名抛 KeyError(编程错误),业务错误(未知 job_id、非法 offset)
   回 `{"error": ...}` dict 给 LLM 看。
2. **三文件三哈希(评审拍板)**。合流文件按到达顺序交错(两个 pump 任务
   同步写、asyncio 单线程天然无竞争),`output_path`/`sha256` 指合流;
   `.stdout`/`.stderr` 分流路径与哈希是 optional 字段——PTY(WP-05)单流
   复用本层时 `split=False`,分流字段为 None。
3. **timeout 默认放宽到 1800s(评审拍板)**,显式 `null` 不限时;`_UNSET`
   哨兵区分"没传"与"传 null"。`list_jobs` 每条带
   `timeout_remaining_seconds`(不限时/已结束为 null)。
4. **进程组强杀**:`start_new_session=True` + `os.killpg(SIGKILL)`。
   kill switch 语义=立即,不做 TERM 协商;整组杀防 `bash -c` 留孤儿。
5. **读流用定长块(64KB)异步迭代,刻意不用行迭代**:`async for line in
   stream` 会把无换行的巨量单行攒进行缓冲——100MB 单行直接撑爆内存,
   正是验收 3 要防的形状。0.80MB 峰值主要来自 64KB 块 × 流数量。
6. **ring buffer 256KB/job,job 完结即释放**:内存只随活动 job 数增长;
   渲染 tail 优先命中 ring,预算大于 ring 容量时回退文件 seek,保证账目
   精确。
7. **文件无缓冲直写**:running 中的 job 也能被 read_output 立刻读到已
   落盘字节(演示中 partial read 已验证);进程崩溃尽量少丢。
8. **账目一律按原始字节**,只有给 LLM 的视图做 UTF-8 `errors="replace"`
   解码——"省略 X 字节"永远能与落盘文件对账。

## 踩坑

1. **并发开发共享 `.venv` 的 editable 安装不稳**:三个 WP 并行开发期间,
   `.pth` 文件内容逐字节核验无误但 site 不加载(`import kalicode` 全仓
   失败),并发窗口内 `pip install --force-reinstall -e .` 连构建依赖都装
   不上。对策:pyproject 的 pytest 配置加 `pythonpath = ["src"]`(pytest
   ≥7 官方机制),一次改动全 WP 受益。**后续 WP 别再去修 venv,直接用
   `.venv/bin/python -m pytest`。**
2. ruff 的 ASYNC230/240 连测试里的 `pathlib.Path.read_bytes()` 都拦;
   测试中小文件阻塞读是有意为之,已在 per-file-ignores 对 `tests/**`
   豁免(见下节声明)。
3. macOS 开发机上 `head -c`、`tr '\000'`、bash printf 八进制转义均可
   用,与 Kali 目标环境行为一致;100MB 测试真实跑(5s 级),不 skip。
