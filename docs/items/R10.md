## 1. 问题、目标与边界

来源：[路线图](../roadmap/2026-09-25-release-roadmap.md)、[评估报告](../reviews/2026-09-25-repository-and-ux-assessment.md)。
评估代码基线：`3a9d07c7da9130e99681a48b5c8975b84b511492`。历史复现是设计输入，不作为本条目已修复证据。

- **来源与依赖**：已知 PTY 无检查点、旧平台批 9；依赖 R01–R03，可提前于 R06 开展。
- **交付**：隔离 PoC 与威胁模型；比较 network namespace＋nftables、独立容器两种方案，确认权限、工具兼容、PTY、DNS、IPv4/IPv6、控制面通信和 cleanup 路径。研究结论先于生产接线。
- **范围/候选文件**：先在隔离 Linux 测试环境和 R 规格与验证记录落证据；必要的合成 fixture 进入 `tests/integration/`（拟新增），不改用户宿主机全局规则。
- **关键限制**：nftables 只能直接表达网络层约束，不能单独验证加密 HTTP 路径、所有通配域动态解析、授权远端内部的再次跳转。远端 shell 的后续出站不受本机规则直接控制。域名绑定、DNS 变化、共享 IP、代理/隧道须明确威胁边界。
- **决策门**：若只能支持 CIDR/端口子集，明确展示该支持矩阵；无法等价执行的规则在受保护模式拒绝启动，不偷偷提升为更宽 IP 授权。R11 未通过前不宣称“任意 scope 均被网络层强制”。

### 实验设计（R10-B 修订，2026-10-25）

本节是现行实验设计；与 R10-A 的保留 raw、B 形态 2 使用 internal net-in、
Docker 默认无 IPv6 等旧描述冲突时，以本节及下方真实实录为准。R10-A 的
基线输出保留作历史，不把后续修订伪写成当时已验证。

**实验环境基线**（`test_baseline_harness_selfcheck` /
`test_baseline_environment_record` 每次重新采集）：

| 项 | 值 |
|---|---|
| 宿主机 | macOS（Darwin 25.3.0，arm64），Docker Desktop 29.2.1，client/server 同版 |
| 实验内核 | 6.12.72-linuxkit（aarch64，Docker Desktop linuxkit VM 共享内核） |
| 基础镜像 | `docker.m.daocloud.io/library/debian:12-slim`，本次镜像 ID `sha256:7c7b2c966bc9ee8cedfeef67e0e279108992c77681fa595db4a9d65c06ccc587`；只读 inspect 后构建，缺失时明确失败，不隐式从 Docker Hub 拉取 |
| 实验镜像 | 每次会话唯一的 `foam-r10-lab:<tag>`；经 TUNA 源安装 iproute2/nftables/iputils-ping/dnsutils/curl/python3/procps/bsdutils/dnsmasq-base；另提供无 setuid/文件 capability 的 ping 副本，只走非特权 ICMP |
| 容器内版本 | Debian 12.15；nftables 1.0.6；iproute2 6.1.0；Python 3.11.2；curl 7.88.1；dnsmasq 2.90；util-linux 2.38.1；宿主编排 Python 3.12.14 |

方案 A 的特权容器只是隔离 Linux 控制面，真实 netns/nftables 规则由
linuxkit 内核执行；方案 B 使用普通 Docker 双栈网络与容器内 gw。**这不是
裸 Kali、裸 Linux Docker 或真实 Kali 工具集验收**，也不能把 NAT66、DNS、
capabilities 等结果自动推广到这些环境。当前 Docker daemon 实测可创建
IPv6 网络，旧的「默认无 IPv6」结论已撤销。R10-A 记录的 VMware SSH 通道
未恢复，本轮没有把它写成可用的裸 Kali 复核通道。

**实验载体与威胁模型**：`tests/integration/` 仅在 `FOAM_INTEGRATION=1`
且 Docker 可达时执行；默认离线套件跳过本目录，显式 opt-in 的全通过才
作为研究证据。宿主 pytest 只编排，实验流量只在合成容器/netns 内。
R10 不修改产品执行接口，也不把 fixture 的显式网络白名单冒充为现有任意
`Scope` 已完成编译。受保护上下文统一为 UID/GID 65534、全部 capabilities
清除、`no-new-privs=1`；无 raw socket、NET_ADMIN、管理套接字或可写控制面
状态。A 的特权 harness 是研究控制面，不是 R11 最小权限 helper 的交付。

**端点独立判据**：HTTP marker 记录唯一 token 路径；dnsmasq 记录 `.test`
查询；端点 raw 接收器只记录 ICMP/ICMPv6 echo-request，ping pattern 是
独立 token。允许须被测侧 rc=0 且端点有 token；拒绝须 rc≠0 且端点无 token，
并有控制面或 bystander 健康正对照。marker/DNS/ICMP 文件必须严格读取成功，
读取失败即测试失败，不能解释成拒绝成功。A 的证据由 root 所有且被测 UID
不可写，B 的证据在独立容器文件系统。规则篡改另验实际 capabilities、
控制面 ruleset 哈希及篡改后的允许/拒绝。

**方案 A 拓扑**（netns+nftables）：

```
harness/root ns：控制面 HTTP :9090，v-test-r 10.10.0.1/30、fd00:10::1
  nft inet r10：forward policy drop + 双族白名单；input 只额外允许 ND 后 drop
  ├─ v-epin-r  10.10.10.1/28、fd00:20::1
  └─ v-epout-r 10.10.20.1/28、fd00:30::1
[tested] 10.10.0.2、fd00:10::2 → [epin] .11 HTTP 8080/8081、UDP DNS
         普通 bash/PTY/后代       [epout] .11 HTTP 8080、UDP DNS（界外）
```

白名单为 tested→`10.10.10.0/28` 的 tcp/8080、udp/53、ICMP echo-request，
以及 tested→`fd00:20::/64` 的同三类规则。仅 epin→tested 的 established
回包可返回，不在白名单前宽放全部 established/related。input 仅放行
ICMPv6 邻居发现 NS/NA 后丢弃 tested→root 流量；曾有全 drop 阻断 ND 的
失败实录，不能删除这条必要链路规则。单 ip 族配置另有 v6 泄漏负面对照。

被测包装为 `ip netns exec tested` → `unshare --mount --pid --fork
--mount-proc` → 非 root/零 capabilities 的 `setpriv`。另以只读父 netns
句柄验证不能 setns 逃逸。`ping_group_range` 只开放非特权 ICMP；raw INET
和 AF_PACKET 创建均须失败。研究控制面按 PID+启动时间+命令身份管理服务，
不按命令行正则 `pkill`。

**方案 B 拓扑**（独立容器）：

- 形态 1 是 IPv4 `--internal` 网 `172.29.0.0/24`，只证明成员级隔离：同网
  8080/8081 均可达，不是 CIDR/端口级 scope；跨网 HTTP 不到端点，daemon
  DNS 对固定上游返回 SERVFAIL 且上游无查询。它不是 R11 的端口护栏候选。
- 形态 2 使用普通双栈网：net-in `172.30.0.0/24`＋`fd00:30::/64` 只容纳
  tested 与 gw；net-out 为 `172.31.0.0/24`＋`fd00:31::/64`。tested 的
  IPv4/IPv6 默认路由由控制面一次性指向 gw；无 NET_ADMIN/NET_RAW 的工具
  不能回指 Docker 网桥或构造二层帧。宿主网桥上不得提供管理面服务，也
  不加入其他不可信同二层成员。
- gw 仅有控制所需的 NET_ADMIN 和 namespaced forwarding，执行 inet 双族
  `/32`/IPv6 地址＋端口白名单、回复方向 established、NAT44/NAT66。input
  允许必要 ND 后拒绝 tested→gw；控制面 HTTP :9090 由 gw 独立出站对照，
  bystander 验证无关流量。Docker 内嵌 DNS 在本版本的上游也经 gw NAT，
  但其他 daemon/平台须另验，优先使用明确的固定解析器而非推断代理路径。

**清理责任**：容器/网络/镜像在创建成功后登记，全部带
`foam.r10.run=<tag>` label，镜像 tag 会话唯一，不覆盖/删除预存 `:local`。
会话清理先按 label 对账，补偿「daemon 已创建、CLI 超时未登记」窗口，再
删除并复查；清理错误、查询非零 rc/异常、任何残留都失败。`finally` 始终写
`$TMPDIR/foam-r10-evidence-<tag>.md`。A 使用函数级 fixture，B 的 crash
容器独立，宿主 PID observer 只有 SYS_PTRACE。

进程回收必须经 `pidfd_open` 绑定身份，再核对启动时间/token 后通过
`pidfd_send_signal` 终止；crash 兜底在发现进程时即持有 pidfd，避免杀 init
后按旧数字 PID 重开导致复用竞态。错误 start/token 保留 canary 有专项探针。
A 的实测还表明降权后 `parent_deathsig=0`，仅杀 unshare 父进程不够：
控制面须按 `NSpid` 找到 PID namespace init 并直接终止。正常 crash 与
readiness 后早失败两路都验证 detached 后代消失、marker 停止增长、
namespace/veth/规则入口消失、独立 HTTP canary/旁观者流量正常。进程消失
采用共享截止时间的轮询，兼容异步回收。未强制制造 PID 快速复用；pidfd
是消除该竞态的内核机制。Docker daemon/宿主崩溃、断电及 pytest 被 SIGKILL
后的自动恢复未在本条实验，label 只提供后续人工/补偿回收入口，归 R11。

| 规则/场景 | R10 结论与 R11 受保护模式要求 |
