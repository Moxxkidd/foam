状态：完成（2026-11-12；AC01–AC06 均有测试与真实行为证据）。来源：2026-11-12 由 [R13–R27 方案评估](../reviews/2026-11-12-r13-r27-plan-review.md) F1 提出；同日用户确认纳入 v0.2.0）。目标版本：[v0.2.0（暂定）](../releases/v0.2.0.md)。风险：一般。负责人：待定。
优先属性：必选。实施状态：完成；TUI 与 CLI 已共用单写者锁，本条目无发布结果。

## 问题与范围

- **来源**：[R02](R02.md) 只为 CLI run/resume 接了 `engagement.lock`，TUI 未接，登记为剩余风险（R02 §8「fork 风险依旧」）；[R03](R03.md) §7 D3 维持不接。实施前 [tui/app.py](../../src/foam/tui/app.py) 以 `RunRuntime(lock=None)` 运行。
- **可复现后果**：TUI 运行期间，对同一目录执行 `foam resume` 不会被拒，两个进程同时追加 `audit.jsonl`，哈希链分叉；两个 TUI 打开同一目录也一样。protected 模式下还会为同一 engagement 创建两套执行边界。
- **目标与可观察行为**：TUI 与 CLI 共用 R02 单写者锁。任一写者持锁时，另一写者（TUI 或 CLI）在首次写审计前被拒，并显示中文原因；锁随进程退出或崩溃由内核释放。
- **排除项**：不做任务列表或「打开已在运行任务」的界面（归 R15）；不处理不持锁的旧版本进程（残余风险照旧登记）；不改锁的实现方式（仍为 flock）。
- **依赖与涉及文件**：依赖 R02/R03（完成）。涉及 `src/foam/tui/app.py`（所有 Engagement create/open 入口）、`src/foam/runtime.py`（`lock` 字段已存在，无需改契约）、`tests/test_tui.py`。

## 方案与评审

- **方案**：TUI 现有多处 `Engagement.create/open` 入口（文件 scope 首条消息、NL 预声明仪式、取消后重发、`start_run`），收敛为一个「打开并取锁」的私有辅助函数。取锁时机必须早于该目录的第一次 `AuditLog` 追加。从 NL 仪式到正式 run 全程持锁，仪式取消且不再使用该目录时释放。锁对象交给 `RunRuntime.lock`，由 `close_run` 按既有顺序最后释放。
- **失败呈现**：`EngagementLockedError` 在 TUI 中显示「该 engagement 已有另一个运行中的写者」，并建议换 `--workdir` 或等待对方结束；不进入运行，不写审计，不创建执行边界。
- **兼容与回退**：锁文件名、语义与 R02 一致，CLI 行为不变。回退即移除 TUI 取锁，恢复 R03 D3 现状。旧版本 TUI 进程仍不持锁，属已登记残余风险。
- **与 R13 的关系**：R28 落地后 CLI 和 TUI 运行都持锁，R13 status 可把 `/proc/locks` 佐证（D1）覆盖到 TUI；R13 的心跳设计不受影响。
- **评审**：2026-11-12 方案评估提出，同日用户确认纳入 v0.2.0（纳入版本不等于授权实施，开工仍需明确授权）；开工前须按 R13 §2.1 的方式复核 TUI 各入口的当前代码。

## 完成与交接

- 关键取舍：所有 file/NL create/open 入口统一经「打开并取锁」助手，在任何审计或修订写入前持锁；启动型 NL 仪式把锁交给正式 run，取消或失败时释放；正式 run 的正常、错误及部分清理由 `close_run` 最后释放锁。未修改 flock、CLI 锁语义、scope、`_trusted_source` 或 R11 能力边界。
- 验收证据：AC01–AC06 对应测试与真实行为见上节；完整离线、ruff/diff 结果见实施记录。R15 AC04 可引用本条目证据。
- 残余风险与迁移提示：旧版本 TUI 进程仍不持锁，不能与新版形成互斥；`engagement.lock` 是 flock 协调载体，**不得手删锁文件**（删除可能使不同写者锁住不同 inode），应等待持锁进程退出/释放或改用其他 `--workdir`。
