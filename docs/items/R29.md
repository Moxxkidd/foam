# R29 · protected 模式的受支持安装与部署形态

状态：规格中（2026-11-12 由 [R13–R27 方案评估](../reviews/2026-11-12-r13-r27-plan-review.md) F2 提出；同日用户确认纳入 v0.2.0）。目标版本：[v0.2.0（暂定）](../releases/v0.2.0.md)。风险：高（涉及 root 运行与密钥传递）。负责人：待定。
优先属性：必选。实施状态：未开始；无本条目测试或发布结果。

## 问题与范围

- **来源**：[R11](R11.md) protected 启动 helper 前，`_trusted_source` 要求 `sys.executable` 与 `network_helper.py` 的解析路径逐级为 root 所有且不可被组或他人写入（[guard/network.py](../../src/foam/guard/network.py)）。这是防止普通用户篡改 root helper 的必要安全条件，不得放宽。
- **问题**：
  1. README「快速开始」推荐 `pipx install .`，包会装在用户目录，helper 源路径必然不可信，protected 直接拒绝启动。用户按文档安装后，protected 模式无法使用。
  2. Kali 采用 PEP 668，`sudo pip install` 默认被拒，不存在「直接装到系统路径」的平滑路线。
  3. protected 需要以 root 启动 Foam：sudo 默认清除环境变量，`FOAM_LLM_API_KEY` 等无法传入；`sudo -E` 又会带入全部环境，破坏 R11「工具不继承模型密钥」的最小环境意图。
  4. root 运行产生的 engagement 目录为 root 所有、0700，之后普通用户执行 `report`/`verify`/`status` 无法读取，没有给出约定。
  5. R11 的实机验证在 Docker/linuxkit 中完成（路径全为 root 所有），没有覆盖真实安装形态；裸 Kali 验证通道尚未恢复。
- **目标与可观察行为**：给出并在真实 Kali 上验证至少一种受支持的 protected 安装形态，例如由 root 创建、位于 `/opt` 下的 venv。文档写明安装、启动、密钥传递和产物属主的约定；`foam doctor`（R13）能指出当前安装是否满足条件，以及具体的处置方法。
- **排除项**：本条目不做 .deb 打包（Debian/Kali 官方源是长期目标，可另立条目）；不放宽 `_trusted_source`；不自动 sudo、不自动修改权限；不改变 legacy 的安装方式。
- **依赖与涉及文件**：依赖 R11（完成）；R29-B 依赖 R13-B 的 `exec.protected` 检查。涉及 `README.md`、发布说明、R13 doctor 处置文案、可能新增的安装辅助说明文档；原则上不改 `guard/` 代码。

## 方案与评审

- **候选形态（待评审定案）**：
  - A：`sudo python3 -m venv /opt/foam && sudo /opt/foam/bin/pip install <wheel>`，以 `sudo /opt/foam/bin/foam ... --execution-mode protected` 启动。需核实 venv 的解释器解析到 root 所有的系统 Python，且 `/opt/foam` 各级不可被组或他人写入。
  - B：系统包形态（.deb），长期正解，但超出本条目范围。
- **密钥传递**：评审 `sudo --preserve-env=FOAM_LLM_API_KEY,FOAM_ANTHROPIC_API_KEY,...` 白名单形式与 root 专用 `.env` 两种方式；禁止推荐 `sudo -E`；文档写明密钥只进入控制面，不进入工具环境（R11 既有保证）。
- **产物属主**：评审两种约定：结项后 chown 给调用用户（`SUDO_UID`），或要求 report/verify 也以 root 执行。须与 R02 的 0700 权限、R09 只读核验一致，不得削弱 engagement 目录的私有性。
- **兼容与回退**：纯文档与诊断层改动，回退即恢复旧文档；已有 legacy 用户不受影响。
- **评审**：2026-11-12 方案评估提出，同日用户确认纳入 v0.2.0（纳入版本不等于授权实施，开工仍需明确授权）；候选形态须在真实 Kali 上验证后再写进 README。
