# WP-03:LLM 后端(provider 接口 + OpenAI 兼容层 + Claude)

状态:pending|依赖:无(首批可开工)

## 目标

后端中立的 LLM 接入层:

- `backends/base.py`:统一接口——`chat(messages, tools) -> 事件流`
  (text 增量 / tool_call 完整帧 / usage)。tool_call 参数归一化为
  `{name, arguments: dict}`;模型差异不泄漏到上层。
- `backends/openai_compat.py`:OpenAI 兼容端点万能适配
  (`base_url`/`model` 可配),实测目标:Kimi K3(优先)、DeepSeek、GLM、
  OpenRouter。API key 只走环境变量(`KALICODE_LLM_API_KEY`)。
- `backends/claude.py`:Anthropic Messages API(httpx 直连,不引 SDK,
  控制依赖面);key 走 `KALICODE_ANTHROPIC_API_KEY`。
- 流式优先;tool calling 必须有;连接失败/限流/内容审核拦截 → 结构化
  错误类型,上层可区分"网络问题"与"provider 拒绝"。

## 实测任务(写进开发日志,如实记录)

- Kimi K3:渗透框架类 system prompt + 严格 tool calling 的**纪律性**
  (参数合法 JSON 率)与**审核容忍度**。被 provider 拦截就如实记录拦截
  文案与复现率;**严禁改写 prompt 去规避审核**。
- 每个后端记录:模型 id、端点、首 token 延迟、tool_call 成功率。

## 排除项

- 多后端 failover/负载(v1)。
- agent 主环(WP-04 消费本接口)。

## 验收标准

1. 契约测试:同一个 fake HTTP server 分别按 OpenAI/Anthropic 两种格式
   应答,两个实现产出**逐字节相同**的归一化事件序列。
2. 错误分类单测:超时/5xx/审核拦截(带特征文案的 4xx)分别映射到
   正确错误类型。
3. 配置单测:base_url/model/env key 注入;缺 key 时报错信息不含任何
   key 片段。
4. 开发日志含 Kimi K3 实测记录(纪律性 + 审核表现)与其余后端的
   连通性记录。
